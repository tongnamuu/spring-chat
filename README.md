# Spring 기반 무중단 대용량 채팅 시스템 (`spring-chat`)

PostgreSQL, Apache Kafka, Redis 및 Spring Boot 4.1 기반의 고성능, 확장 가능한 무중단 대용량 실시간 채팅 시스템입니다.

---

## 🛠️ 주요 요구사항 및 특징

1. **최대 1,500명 정원의 그룹 채팅방**
   - 기본 정원은 50명이며, 방 생성 시 최대 1,500명까지 설정 가능.
   - PostgreSQL 방 단위 잠금으로 동시 입장 시 인원 갱신 충돌 및 정원 초과 방지.
   - 정원 설정 지원과 1,500명의 실시간 처리 성능 검증은 별개이며, 아래 확장 전략 참고.
2. **1대1 개인 채팅 (DIRECT)**
   - 최대 인원 2명 자동 고정 및 상대방 초대 연동.
3. **공개(PUBLIC) & 비공개(PRIVATE) 채팅방**
   - 방 종류별 검색 및 입장 제어.
4. **초대 코드(Invite Code) 기반 입장**
   - 모든 방은 고유 8자리 초대 코드가 자동 생성되며 코드를 통한 원클릭 입장 지원.
5. **참여 채팅방 전용 목록 조회**
   - 유저별 `chat_room_member` 매핑 기반으로 본인이 참여한 방만 빠르게 조회.
6. **Zero-Downtime WebSocket 배포 전략**
   - `server.shutdown=graceful` 적용으로 기존 연결 정리 시간 확보.
   - 클라이언트 자동 재접속 및 미수신 메시지 복구로 배포 시 연결 중단에 대응.
   - Redis 로그인 세션 공유 및 Kafka 기반 WS 노드 간 메시지 배포. 소켓과 구독 상태는 각 WS 노드가 관리.

## 🏗️ 멀티 모듈 아키텍처

```
spring-chat/
├── chat-common/       # DTO, Enums (RoomType, MessageType), ErrorCode, Exception
├── chat-core/         # JPA Entities, Repositories, Business Services
├── chat-api/          # REST API Controllers (User, Room Management, Message History)
├── chat-ws/          # WebSocket / STOMP Gateway, Kafka Producer, Session Manager
└── chat-consumer/    # Kafka Consumer (PostgreSQL Bulk Persistence Worker)
```

## 사용자·메시지 증가에 대응하는 확장 전략

### 목표와 전송량

확장 목표는 **한 방에 1,500명, 초당 10,000건의 메시지, 모든 클라이언트가 원문을 1초 이내 수신**하는 것입니다.
이는 설계 및 검증 목표이며, 현재 달성한 성능을 의미하지 않습니다.

모든 사용자에게 모든 원문을 전달하면 필요한 전송량은 다음과 같습니다.

```text
초당 전달 횟수 = 방의 사용자 수 × 초당 메시지 수
초당 원문 전송량 = 사용자 수 × 초당 메시지 수 × 직렬화된 메시지 크기

1,500명 × 10,000건/초 = 초당 15,000,000회 전달
메시지당 500바이트 가정: 서버 전체 약 7.5GB/초 = 60Gbps
사용자 한 명의 수신량: 약 5MB/초 = 40Mbps
```

위 계산은 프로토콜 오버헤드를 제외한 값입니다. 배치는 프레임 수와 처리 비용을 줄이지만
원문 데이터량 자체를 줄이지는 않습니다. 압축 효과도 실제 메시지 내용으로 측정해야 합니다.

### 저장과 전달을 분리하는 구조

```text
발신자
  → 수신 서버
  → Kafka 원본 메시지 (roomId 기준 파티션)
  → DB 배치 저장 및 커밋
  → Kafka 저장 완료 메시지
  → 여러 WebSocket 서버
  → 각 서버에 연결된 사용자
```

메시지는 사용자 수만큼 저장하지 않고 메시지당 한 번 저장합니다. 같은 방의 사용자도 여러
WebSocket 서버로 나누고, 각 서버는 자기에게 연결된 구독자에게만 전달합니다.
DB에 저장된 메시지를 배포하므로 실시간 수신과 재접속 복구에 같은 메시지 ID를 사용할 수 있습니다.
실패 후 재처리로 중복 전달이 발생할 수 있으므로 저장 및 클라이언트 양쪽에서 중복을 제거합니다.

### 부하 종류별 대응

| 증가하는 부하 | 대응 방향 |
| --- | --- |
| 접속 사용자 수 | WebSocket 서버와 네트워크 용량 확장, 같은 방의 접속자도 여러 노드에 분산 |
| 입력 메시지 수 | 수신 서버 확장, 배치 입력, 인증·세션 확인 비용 최적화 |
| 채팅방 수 | 방 기준 Kafka 파티션 및 소비자 확장, 해당 방의 구독자가 있는 노드에만 배포하는 라우팅 도입 |
| 한 방에 집중되는 메시지 | 방의 순서를 정하는 처리는 유지하고, 저장·전송을 배치화하며 사용자 전달 작업을 여러 노드로 분산 |
| 저장 이력 | 배치 저장, 방/메시지 ID 인덱스, 기간별 테이블 분할·보관 기간·아카이브 정책 적용 |
| 브라우저 수신량 | 수신과 렌더링 분리, 프레임별 화면 갱신, DOM 및 메모리 상한 적용 |

같은 방을 같은 Kafka 파티션에 넣으면 파티션 내 순서를 사용할 수 있지만, **파티션을 늘리는
것만으로 한 방의 처리량이 자동으로 늘지는 않습니다.** 운영 중 파티션 수를 변경하면 방의
키 배치가 바뀔 수 있으므로, 순서를 유지하는 전환 절차가 필요합니다.

프레임마다 DB 인증 조회를 반복하는 비용은 줄여야 하지만, 탈퇴·권한 회수 시 즉시 차단하는
동작은 유지해야 합니다. 연결 시 인증과 이후 권한 변경 전파를 분리하는 방식으로 개선합니다.

### 전송·FE·복구 정책

- 전송은 수십 ms 또는 최대 건수·바이트 상한을 기준으로 묶어 프레임 수를 줄입니다.
- 클라이언트는 모든 원문을 수신하고 중복을 검사하되, 화면에는 최근 또는 보이는 범위만 렌더링합니다.
  현재 구현은 최근 500개를 화면에 유지하며 원문 이력은 서버에 저장합니다.
- 마지막 처리 메시지 ID와 배치의 직전 메시지 ID로 누락을 확인하고, 페이지 단위로 이력을 복구합니다.
- 느린 수신자의 대기열을 무한히 늘리지 않습니다. 상한을 넘으면 연결을 종료하고 재접속 시 복구합니다.
- 입력에도 대기량 제한과 과부하 제어가 필요합니다. executor 큐 제한만으로 연결별 순서 큐까지 제한되지는 않습니다.

회선의 지속 수신 속도가 메시지 유입 속도보다 느리거나 연결이 끊긴 클라이언트에는 1초 전달을
보장할 수 없습니다. 정상 연결의 실시간 전달 목표와 장애 후 복구 목표를 구분해야 합니다.

### 적용 순서와 운영 지표

1. **입력 병목 제거:** 인증 조회, Redis 세션 갱신, 연결별 순서 처리 및 입력 큐를 측정하고 개선합니다.
2. **저장·배포 배치화:** DB 저장과 Kafka 배포를 묶고, 재처리 시 중복 제거와 누락 복구를 확인합니다.
3. **WebSocket 분산:** 노드당 소켓 수와 실제 전송량을 기준으로 접속자를 분산합니다.
4. **네트워크·저장 용량 확보:** 전체 전송 대역폭, DB 쓰기 처리량, Kafka 복제 및 이력 보관 정책을 준비합니다.
5. **목표 규모 검증:** 분리된 서버와 여러 부하 생성기로 1,500명·초당 1만 건을 지속 검증합니다.

확장 판단에는 접속자 수뿐 아니라 Kafka 적체 시간, 입력·전송 대기량, DB 배치 처리 시간,
네트워크 사용량, JVM 메모리·GC, 재접속 횟수 및 실제 클라이언트 수신 지연을 사용합니다.
모든 사용자에게 1초 이내 전달하는 조건은 평균이나 p99만으로 확인할 수 없으므로 최대 지연과
미수신 건수도 확인해야 합니다. 클라이언트 간 도착 시각 차이도 별도로 측정합니다.

### 현재 구현과 검증 범위

현재 작업에는 DB 배치 저장, 저장 완료 후 Kafka 배포, WS 세션별 전송 대기량 제한,
FE 배치 렌더링, 누락 복구, 정원 1,500명 설정 및 동시 입장 충돌 수정이 반영되어 있습니다.
방별 선택적 노드 라우팅, 입력 순서 큐의 명시적 바이트 제한, 인증·세션 경로 최적화,
운영용 복제·보관 정책은 후속 작업입니다.

기능 회귀 및 브라우저 테스트는 통과했습니다. 로컬에서 50명에게 초당 1만 건을 5초간 보내
총 250만 회 전달을 누락·중복·순서 역전 없이 완료했지만, **최대 수신 지연은 약 17.6초로
1초 목표에 미달**했습니다. 이 수신 결과에는 송신 종료 후 대기 시간이 포함됩니다.
1,500클라이언트 전체 성능 시험은 실행하지 않았습니다.

자세한 내용은 [설계·구현 계획](docs/high-throughput-chat.md)과
[2026-09-17 측정 결과](docs/high-throughput-results-2026-09-17.json)를 참고하세요.

## 🚀 실행 가이드

### 1. 인프라 실행 (Docker Compose)
PostgreSQL, Redis, Apache Kafka, Zookeeper를 로컬에서 실행합니다:
```bash
docker-compose up -d
```

### 2. 애플리케이션 빌드 및 테스트
```bash
./gradlew build
./gradlew test
```

로그인 브라우저 E2E는 전체 Docker 스택을 실행한 뒤 별도로 수행합니다:

```bash
cd e2e
npm install
npm test
```

성공 화면은 `artifacts/e2e/chat-1-login-success.png`와
`artifacts/e2e/chat-2-withdrawal-success.png`에 저장됩니다.

### 3. 모듈별 실행
- **REST API Server (8080 포트)**:
  ```bash
  ./gradlew :chat-api:bootRun
  ```
- **WebSocket Server (8081 포트)**:
  ```bash
  ./gradlew :chat-ws:bootRun
  ```
- **Kafka Consumer DB Worker (8082 포트)**:
  ```bash
  ./gradlew :chat-consumer:bootRun
  ```

## 🔌 API 명세 요약

| Method | Endpoint | 설명 |
| :--- | :--- | :--- |
| `POST` | `/api/auth/signup` | 회원가입 (username, nickname, password, 성공 시 201) |
| `POST` | `/api/auth/login` | 로그인 및 Redis 세션 쿠키 발급 |
| `GET` | `/api/auth/me` | 현재 로그인 사용자 조회 |
| `POST` | `/api/auth/logout` | 서버 세션 무효화 |
| `DELETE` | `/api/users/me` | 비밀번호 재확인 후 회원 탈퇴 및 전체 세션 무효화 |
| `POST` | `/api/rooms` | 로그인 사용자의 채팅방 개설 |
| `POST` | `/api/rooms/join` | 초대 코드로 방 입장 |
| `GET` | `/api/rooms/my` | 내가 참여한 채팅방 목록 조회 |
| `GET` | `/api/rooms/{roomId}/messages` | 이전 메시지 내역 조회 |
| `GET` | `/api/rooms/{roomId}/sync` | 재연결 시 미수신 메시지 Gap 복구 |
| `WS` | `/ws-stomp` | Redis 로그인 세션이 필요한 STOMP 엔드포인트 |

---

REST와 STOMP 모두 `CHAT_SESSION` HttpOnly 쿠키에서 사용자를 결정합니다. 클라이언트가 보낸
`X-User-Id`, `senderId`, `senderName`은 사용자 식별에 사용하지 않습니다. HTTPS 배포에서는
`SESSION_COOKIE_SECURE=true`를 설정해야 합니다.

회원 생성은 `POST /api/auth/signup`만 사용합니다. 이전 `POST /api/users` 생성 경로는 제거했으며,
username은 영문자로 시작하는 3~30자의 영문·숫자·밑줄 아이디 또는 50자 이내의 이메일을 허용합니다.
password는 8~72자이면서 영문과 숫자를 각각 하나 이상 포함하고, nickname은 앞뒤 공백 없는
2~20자로 제한합니다.

회원 탈퇴는 사용자를 소프트 삭제하고 식별 정보를 익명화합니다. 참여 멤버십과 방 인원을 한
트랜잭션에서 정리하고, OWNER는 가장 먼저 가입한 남은 멤버에게 이전합니다. 남은 멤버가 없는
방은 삭제하지만 기존 `chat_message` 이력은 보존되며 조회 시 발신자를 `탈퇴한 사용자`로 표시합니다.
